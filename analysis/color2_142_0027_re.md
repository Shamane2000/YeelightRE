## 1. RPC-Architektur: zwei Tabellen, ein Namensschema

Alle Yeelight-RPC-Handler heißen `<method>_JsDlgt`. Der Dispatcher baut den Namen zur Laufzeit:

```
0x1f043f27  "%s_JsDlgt"        ; Format-String, von FUN_1f01b152(buf,0x20,"%s_JsDlgt",method) genutzt
```

Es gibt **zwei** Handler-Tabellen mit `{handler_ptr, name_ptr}`-Paaren (8 Byte/Eintrag):

| Tabelle | Adresse | Einträge | Zweck |
| :--- | :--- | :--- | :--- |
| Voll-Tabelle (Cloud/Grid-Kanal) | `0x00103098` | 47 | `test`, `config`, `info`, `restore`, `rpc_test`, `stop_diag_mode`, `wifi_assoc_state`, `get_ota_state`, `get_ota_progress`, `ota`, `reboot`, `config_router`, `xgetKeys`, `xget`, `xdel`, `xset`, `suicide`, … , `get_prop` |
| LAN-Tabelle | `0x00103118` | 31 | **= Voll-Tabelle ab Index 16** (`0x00103098 + 0x80`), also `suicide` … `get_prop` |

Beide Tabellen werden über Literal-Pools in `FUN_1f00fec4` adressiert:

| Pool | Wert | Bedeutung |
| :--- | :--- | :--- |
| `0x1f00ff90` | `0x200009e0` | **LAN-Whitelist** (RAM, NULL-terminiert) |
| `0x1f00ff94` | `0x1f043f27` | `"%s_JsDlgt"` |
| `0x1f00ff98` | `0x000000f8` (248) | Länge LAN-Tabelle in Byte → 31 Einträge |
| `0x1f00ff9c` | `0x00103118` | LAN-Tabelle |
| `0x1f00ffa0` | `0x1f010629` | Antwort-/Send-Callback, den jeder Handler als 2. Argument bekommt |

**Wichtig:** die 31 LAN-Einträge enthalten `set_ps` (Index 10) und `get_ps` (Index 9) — die
Handler sind also vorhanden und über den Cloud-Kanal erreichbar. Der LAN-Zugriff wird *vorher*
per Whitelist gefiltert (§3).

## 2. LAN-Request-Pfad (TCP 54321)

```
LAN-TCP-RX
  └─ FUN_1f010094(client_ctx, buf, len)        ; Request-Parser + Quota-Gate
       ├─ Feld-Extraktion aus JSON ("id", "method", "params") via FUN_1f004292
       ├─ Quota:  if (!*(u8*)(ctx+0x176)) {           ; +0x176 == 1 ⇒ music-mode, kein Limit
       │             if (--*(int*)(ctx+0x70) < 0) return 5;
       │             if (--*(int*)(g_state+0x7c) < 0) return 5; }
       └─ FUN_1f00fec4(ctx, param2, method, params, 0)   ; Whitelist + Dispatch
```

`FUN_1f010094` ist der einzige Aufrufer von `FUN_1f00fec4` mit echten Client-Daten; der zweite
Aufrufer `FUN_1f010074` ist der `127.0.0.1`-Loopback (`0x1f043f70`) mit `param_5 = 1`
(kein Antwort-Alloc). Task-Name des Servers: `lan_ctrl_task` (`0x1f043f7a`).

## 5. AP-Modus / Provisioning — Whitelist-Verhalten (Kernfrage)

**Befund: es gibt keinen AP-Modus-spezifischen Zweig in der LAN-Dispatch-Kette.**

Belege:

1. `FUN_1f00fec4` enthält **nur** Whitelist-Scan + Tabellen-Lookup. Keine Abfrage von
   Provisioning-, STA- oder `wifi_assoc_state`-Flags (die einzige Flags-Abfrage im Umfeld ist
   `param_1+0x176` = music-mode, rein für die Quota-Freistellung und die Handler-Ctx).
2. `FUN_1f010094` prüft vor dem Dispatch ausschließlich die Quota, nicht den WLAN-Modus.
3. Der einzige AP-relevante RPC, `config_router` (Voll-Tabelle Index 11, `0x1f00a085`) bzw.
   `ylk_config_router` (Index 21, `0x1f00cdf5`), ist **weder** in der Whitelist **noch** über
   `FUN_1f00fec4` erreichbar. `FUN_1f00cdf4`/`FUN_1f00a084` haben im Decompilat **keinen**
   direkten Caller — sie werden ausschließlich dynamisch über die Voll-Tabelle gerufen
   (anderer Kanal als LAN-TCP).

➡ Konsequenz für die Ausgangsfrage: **`set_ps` steht im AP-/Provisioning-Modus NICHT auf einer
Whitelist und wird auch nicht „nur im AP-Modus" geblockt — es ist im LAN-Kanal generell
geblockt** (Code 2). Ein Gerät im AP-Modus erreicht man entsprechend nicht über `set_ps`; die
Provisionierung läuft über den UDP-54321-`config_router`-Pfad des App-Handshakes
(siehe `analysis/apk_lan_control_re.md`).

**Patch-Relevanz:** Wer `cfg_lan_ctrl` per LAN setzen will, muss entweder
(a) `set_ps` in die Whitelist `0x200009e0` aufnehmen (RAM-Kopie → muss im Flash-Original der
Initialisierungscopy angepasst werden), oder
(b) den Whitelist-Scan in `FUN_1f00fec4` patchen (z. B. `2` statt Scan zurückgeben → immer
weiter dispatchen; Achtung: gibt dann auch `suicide`/`ylk_config_router` frei).

## 6. LED-/PWM-Treiber & Rate-Limits (Basis für Patches)

### 6.1 Zentrale Apply-Funktion `FUN_1f0110a0` @ `0x1f0110a0` (140 Byte)

```c
(**(code **)(*DAT_1f011130 + 0x2c))(*DAT_1f011130, *(int*)(*DAT_1f01112c + 0x7c) != *param_1);
*(int *)(iVar5 + 0x7c) = *param_1;                 /* aktuelle Brightness 0..100 */
switch (*(int *)(iVar5 + 0x78)) {                  /* Modus */
  case 1: FUN_1f010f20(bright, state[0x6c], state[0x6d], state[0x6e]); break; /* RGB  */
  case 2: FUN_1f010c6c(bright, *(u32*)(state+0x58));                 break; /* CT   */
  case 3: FUN_1f010cf8(bright, *(u32*)(state+0x70), *(u32*)(state+0x74)); break; /* HSV */
}
uVar3 = FUN_1f00f77c((char)param_1[1], param_1[2]);   /* Transition-Rest */
(**(code **)(*piVar2 + 0x28))(*piVar2, uVar3);         /* Treiber-Op +0x28 */
FUN_1f00f9a8(uVar3);
```

Jeder Modus-Pfad baut ein 12-Byte-„Light-State"-Struct (`{brightness, r/g/b}` bzw.
`{brightness, ct}`) und ruft **dieselbe Treiber-Op `+0x44`**:

* RGB: `FUN_1f010f20` — `local_2c._0_3_ = CONCAT12(param_2, CONCAT11(param_3, param_4))`
  → 24-bit RGB, `local_28._0_2_ = bright`.
* CT:  `FUN_1f010c6c` — `local_2c = CONCAT22(local_2c._2_2_, (short)param_2)`,
  `local_28._0_2_ = CONCAT11(1, bright)`; merkt `if (ct < 0xfa1) { state[0x10]=1 } else { state[0x10]=2 }`
  (`0xfa1 = 4001` K = Grenze zwischen „WW/CW-Modus 1" und „Modus 2").
* HSV: `FUN_1f010cf8` (gleiche Signatur, H/S statt RGB).

Der eigentliche PWM-/LED-Register-Zugriff liegt **hinter der Treiber-Vtable** (Slot `+0x44` =
`set_light`, Slot `+0x28` = `transition/commit`, Slot `+0x2c` = `on/off`). Die Vtable wird zur
Laufzeit aus `DAT_1f011130`/`DAT_1f010f98` geladen (somit austauschbarer Treiber — Patch-Ansatz
für „custom PWM" = eigener Handler auf Slot `+0x44`, ohne die Kommandoschicht anzufassen).

### 6.2 LED-Timer

* Timer-Name `led-timer` (`0x1f0425a8`), Fehlerfall `Unable to delete LED timer` (`0x1f0425b2`).
* `FUN_1f0038e8` legt ihn an: `FUN_1f003810(<state>, 200, 800)` → **Periode 200 ms**,
  weitere Parameter 100/200/800 ms (Timer-Structs, 0x38 Byte, via `FUN_1f02bee6` = `xTimerCreate`).
* Zweiter Timer `0x1f003988` (Transition-Timer) mit denselben 200-ms-Rastern.

### 6.3 Rate-Limits / Validierung (Command-Ebene `FUN_1f00e844`)

| Cmd | Bedeutung | Guard im Decompilat | Limit |
| :-- | :--- | :--- | :--- |
| 4 | `set_bright` | `if (*(int *)(param_1 + 4) - 1U < 100)` | 1..100 |
| 5 | `set_ct_abx` | `state[0x60] <= v && v <= state[0x5c]` | dynamisch (Gerätegrenzen) |
| 6 | `set_rgb` | `*(int *)(param_1 + 4) - 1U <= DAT_1f00eaf8` | 1..16.777.215 |
| 7 | `set_hsv` | `v < 0x168 && dur < 0x65` | Hue < 360, Duration < 101 |
| 8 | `set_ct_abx`/Transition | `if (*(uint *)(param_1 + 4) < 0x65)` | Duration < 101 |
| 10 | `set_power`/`toggle` | `FUN_1f00fa6c(...)` → Snapshot von `state+0x58/0x6c/0x70/0x74/0x7c` | — |
| default | unbekannt | `return 4` (`out of memory` als Fallback) | — |

Transition-Semantik: `state+0x7c` = Ziel-Brightness, `FUN_1f00f77c(dur, mode)` liefert den
Transition-Descriptor, `state+0x180 != 0` ⇒ laufende Transition wird abgebrochen
(`FUN_1f00f73c(1)`).

## 7. Offene Punkte / Caveats

1. **Treiber-Vtable-Ziel nicht statisch aufgelöst**: `DAT_1f011130`, `DAT_1f010f98` zeigen auf
   Laufzeit-Zeiger (`.data` wird zur Init aus Flash kopiert). Für die exakte PWM-Registeradresse
   (88MW302-LED-Block) ist ein Init-Trace (`FUN_1f02xxxx`-Registrierung der Ops) nötig —
   alle Kandidaten in `ALL.c` mit `0x44000108` gehören zur Pin-Mux-Init (`FUN_1f03c230`),
   nicht zum LED-Dimmer.
2. `FUN_1f01bcd4`-Aufrufe mit nur einem Argument sind Decompiler-Artefakte (s. §2) — bei
   Cross-Checks immer `strcmp(a,b)` annehmen.
3. Der Kanal, über den `config_router` tatsächlich dispatcht wird (UDP 54321 / Grid), ist in
   dieser Analyse **nicht** lokalisiert (kein statischer Caller) — Kandidat für ein Folgeticket.
